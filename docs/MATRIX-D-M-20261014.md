## 3. 播放：首轮「不可判定」，第二轮换源后**通过**

播放器确实进入了 `VideoActivity` 并显示了完整浮层（标题、时长、码率、简介、按钮），
但**播放没有真正推进**：

```
10-14 15:09:12.055  15046  D VideoActivity: onTimeChanged: isOwner=true mHistory=true
10-14 15:09:12.057  15046  D VideoActivity: onTimeChanged:
        position=-9223372036854775807 duration=2629568 canSave=false
```

- `position = -9223372036854775807`（`Long.MIN_VALUE`）= **位置未知哨兵值**，每秒重复，从未变化；
- `duration = 2629568` ms = 43:50，与界面上的 `00:00 / 43:50` 一致；
- 界面速率恒为 **`0 KB/s`**（同一帧在 15:06:56 曾读到 `26.1 MB/s`，随后归零）。

即：播放器拿到了时长，但**没有拿到可播放的流**，进度始终停在起点。
对照 `MATRIX-D-T-20261014.md` §1 —— 那一行的音频播放有真实推进
（`PlaybackState {state=3, position=53919}`），所以不是"本行观测方法不对"，而是**这个源/这部剧在本机没有起播**。

**因此「播放无回归」既不能判通过，也不能判失败——记为不可判定。**
**（第二轮已撤回该结论：换源后播放正常，见 §3.5。）**

### 3.3 换第二部片复测（同为不可判定）

按 §7 的判据换了一部**电影**（`爆烈房客` / `Tenement.2026.1080p.VMX.WEB-DL.H.264.AAC.mkv`，
时长 `1:30:16`）重跑：

| 项 | 结果 |
|---|---|
| 进入播放器 | ✅ `VideoActivity`，拿到 `duration=5416020` ms = 1:30:16 |
| `onTimeChanged` 的 `position` | ❌ 仍恒为 `-9223372036854775807`（`Long.MIN_VALUE`） |
| 界面速率 | ❌ 恒为 `0 KB/s` |
| 播放器引擎错误日志 | **无**（600 行内无 `ExoPlayer`/`MediaCodec`/`HttpDataSource`/`403`/`404`/超时） |

即**同一源下的第二部片也不起播**（2/2）。这削弱了"单部片坏"的解释，
但仍**不能**据此判定播放器回归——该源是"盘"类站点，其直链是否可用不受本仓库控制。

### 3.4 一个必须记录的方法论陷阱

为判断"画面到底有没有在动"，取相隔 6 秒的两帧做逐像素差，得到 **75.9% 像素变化**，
看起来像"视频在播"。但**这个结论是错的**：该详情浮层的背景是 **TMDB 背景图轮播**，
日志里可见 `TmdbHeaderView: 轮播切换到第 N 张`，轮播动画本身就会让全屏大幅变化。

**所以本行的播放判据只认 `onTimeChanged` 的 `position` 是否单调推进，不认帧差。**
（`MATRIX-D-T-20261014.md` 那行之所以可用，是因为它的音频播放有真实推进的 `PlaybackState`。）

### 3.5 第二轮：换源后**播放正常起播**（通过，撤回首轮「不可判定」）

按首轮 §7 的建议，换**另一个配置源**（`热播[采]`，非同一源的别的片）重跑。
片目：`藏海传` 第 1 集（`duration=2698840` ms = 44:59）。

#### 3.5.1 决定性证据：`position` 单调推进

`logcat` 连续采样（每秒一条，增量恒为 ~1000ms）：

```
D VideoActivity: onTimeChanged: position=9839  duration=2698840 canSave=true
D VideoActivity: onTimeChanged: position=10833 duration=2698840 canSave=true
D VideoActivity: onTimeChanged: position=11833 duration=2698840 canSave=true
D VideoActivity: onTimeChanged: position=12835 duration=2698840 canSave=true
D VideoActivity: onTimeChanged: position=13842 duration=2698840 canSave=true
```

`position` **单调递增且步长等于真实墙钟秒数**，`canSave=true`
（首轮那台设备的症状是 `position` 恒为 `Long.MIN_VALUE`、`canSave=false`，两者形成鲜明对照）。

同时媒体会话层可见真实播放状态：

```
V NewAvrcpMediaPlayerWrapper: onPlaybackStateChanged():
  PlaybackState {state=3, position=9746, buffered position=63480, speed=1.0, ...}
```

`state=3` 即 `STATE_PLAYING`。

#### 3.5.2 画面与进度条同步推进

| 文件 | 界面进度 |
|---|---|
| `D-M-32-player.png` | `00:13 / 44:59`，可见真实视频帧 |
| `D-M-33-osd.png` | `00:59 / 44:59` |
| `D-M-37-controls.png` | `08:28 / 44:59` |
| `D-M-38-progress-1p5x.png` | `17:21 / 44:59`（此时已切到 1.5 倍速，见 §4.2） |

界面进度与日志 `position` 一致，且**画面是真实影片帧**（不是首轮那种静态背景轮播）。

#### 3.5.3 首轮结论的归因

首轮「2/2 部片不起播」是**该源（`木偶[盘]`）当次不可用**，不是播放器缺陷。
换源即恢复，与首轮 §6 的保留意见一致（「不能据此推断播放器本身有缺陷」）。
**故「播放无回归」判定为通过**；首轮 §3.3 的「同源第二部片仍不起播」记录保留，
作为该源当时状态的证据，不再作为本行判定依据。

### 4.3 字幕：未取证（入口已定位）

字幕入口是控制层里 `action.text` 按钮的**长按**，链路已从代码定位：

```
view_control_vod_action.xml:95-99   id/text   tag="3"  text=@string/play_track_text
VideoActivity.java:1685             mBinding.control.action.text.setOnLongClickListener(view -> onTextLong())
VideoActivity.java:5299-5303        onTextLong(): if (!player().haveTrack(C.TRACK_TYPE_TEXT)) return false;
                                                 onSubtitleClick();
VideoActivity.java:7844-7846        onSubtitleClick(): SubtitleDialog.create()...show(this)
```

**未取到证据的原因**：`onTextLong()` 在**流内没有文本轨时直接返回 false**，
本次播放的 `热播[采]` 该集未观察到文本轨，长按无响应，故字幕对话框未弹出。
按「未取证」记录，**不判失败**——这是流的属性，不是字幕功能回归。

## 6. 局限

1. 首轮同源试了 **2 部**片都停在起点；第二轮换源（`热播[采]`）后正常。
   两轮合并的结论是**该源当次不可用**，不是播放器缺陷——但**未逐源复现**，
   故「源可用性」本身不在本行结论内。
2. **不要用帧差判断播放**：本播放器的详情浮层背景是 TMDB 轮播，会让全屏像素持续变化（§3.4）。
   本行判据始终是 `onTimeChanged` 的 `position` 单调性。
3. 字幕未取证（§4.3）：需要一个**确实带文本轨**的流才能复验。
4. 设备是 1080×1920 的 LDPlayer 模拟器，不是真机；且第二轮期间设备经历了一次重启
   （`systemui` ANR），重启后本行未重复全部步骤。
5. 未做触控与 D-pad 双路径的可达性遍历。
6. 倍速只验证了 `1.0 → 1.5` 一档；0.5/2.0/5.0 等极值档未逐一验证。
